# Верификация номера телефона — контракт интеграции

*Перевод `docs/verification-api.md` от 25.09.2026; при расхождении прав английский оригинал.*

Как приложение просит этот шлюз подтвердить, что человек владеет номером телефона, и как оно получает ответ. Четыре HTTP-вызова и один необязательный пуш.

Ничего здесь не меняет `POST /sms/send`, `GET /sms/{id}` или вебхук доставки. Верификация — не сообщение, которое вы отправляете: вы никогда не составляете текст, никогда не выбираете, чем его доставить, а на большинстве маршрутов текста вообще не существует.

> **Статус.** Двери ниже построены и протестированы. Какие маршруты конкретное развёртывание способно фактически провести — вопрос конфигурации, и об этом сказано в разделе [Что развёртывание может провести сегодня](#что-развёртывание-может-провести-сегодня) — прочтите этот раздел, прежде чем планировать дату релиза.

## Общая форма

```
POST /verifications              → id + the routes that can carry it right now
POST /verifications/{id}/route   → you pick one; the person is told what to do
   … the person acts: types the code back, calls us, or texts us …
POST /verifications/{id}/check   → only when the person types the code back to you
GET  /verifications/{id}         → the truth, at any moment
```

Два момента в этой форме важны для дальнейшего.

**Вы не выбираете механизм — вы выбираете из того, что предлагаем мы.** Вы никогда не называете нам оператора, вендора или SIM-карту и никогда не держите у себя таблицу того, какие сети работают. Вы отправляете номер; мы отвечаем маршрутами, которые могут доказать *в этот момент*, что способны его провести, — от самого дешёвого. Молча берите первый или покажите человеку весь список. Оба варианта обслуживаются одним и тем же ответом.

**Никогда не зашивайте имя маршрута в код.** Набор маршрутов — это конфигурация, и он растёт. Пишите код по списку, который вам прислали, в том порядке, в котором его прислали; отображайте тот `instruction`, который вам дали. Приложение, написанное так, не потребует изменений, когда маршрут добавят, уберут или переставят местами.

## Аутентификация

Так же, как и в остальном API: `Authorization: Bearer <token>`, один токен на приложение, выданный оператором через `/admin/apps`. Базовый URL — собственный URL развёртывания.

Верификация принадлежит приложению, которое её создало. Если другое приложение запрашивает её по id, оно получает `404`, а не `403` — оно не должно узнать даже, что такой id существует, и уж тем более потратить на него попытки.

## POST /verifications

Открыть верификацию. **Этим вызовом ничего не размещается, не отправляется, не звонится и не тарифицируется.** Всё, что он стоит, — это набор проверок предусловий, и они ограничены как единое целое.

```http
POST /verifications
Authorization: Bearer <your token>
Content-Type: application/json

{
  "phone": "<the subscriber's number — E.164, or national; we normalise it>"
}
```

`phone` — единственное поле. Запрос, называющий маршрут, вендора, оператора — или задающий собственный код, — отклоняется целиком, а не выполняется частично.

### Ответ 200

```json
{
  "id": 9,
  "status": "pending",
  "routes": [
    {
      "route": "call_in",
      "instruction": "Call <number> from the number being verified. The call is not answered and costs you nothing; hang-up is ours.",
      "number": "<number>"
    },
    {
      "route": "sms_in",
      "instruction": "Text the code you were shown to <number> from the number being verified.",
      "number": "<number>"
    },
    {
      "route": "flash_call",
      "instruction": "Wait for a call to the number being verified and read the code off the calling number: it is the last four digits. Do not answer the call.",
      "number": null
    }
  ]
}
```

| поле | значение |
|---|---|
| `id` | идентификатор верификации. Используйте его во всех последующих вызовах. **Это не идентификатор сообщения** — два пространства id пересекаются уже с первой строки каждой из таблиц |
| `status` | `pending` |
| `routes` | что может провести её прямо сейчас, **от самого дешёвого**. Никогда не бывает пустым при `200` |

`instruction` — это то, что должен сделать человек, словами, по которым можно действовать. Он называет адрес и никогда — личность: какая SIM-карта отвечает, чей вендорский счёт платит, какой модем стоит в стойке — ничего из этого не видно ни вам, ни ему. См. [Инструкция на английском](#инструкция-на-английском), прежде чем строить на этом экран.

`number` — тот же адрес, но **как данные**, и именно его нужно читать, если вы пишете собственный текст. Он несёт номер, на который абонент должен позвонить или написать, на маршрутах, где это требуется от него (`call_in`, `sms_in`), и равен `null` на каждом маршруте, где действует сам шлюз, — там человеку набирать нечего, а номер был бы адресом туда, где никто ничего не ждёт.

Это поле **добавлено дополнительно**: оно появилось 22.09.2026, у него есть значение по умолчанию, и приложение, написанное до этого, не пострадает.

Маршруты, у которых `instruction` пуст, — это те, где человеку остаётся только ждать: сообщение или звонок приходят к нему сами.

### Отказы

| статус | тело | когда |
|---|---|---|
| `422` | `{"detail": {"error": "no_route_available", "message": "…"}}` | ничто не может доказать, что способно провести этот номер сейчас. **Верификация не открывается** — мы не выдаём вам сессию, единственный возможный исход которой — истечь |
| `422` | `{"detail": {"error": "number_blacklisted", "phone": "…"}}` | номер находится в чёрном списке шлюза |
| `422` | `{"detail": [ … ]}` | обычная валидация: номер не разбирается для настроенного региона, либо использовано поле, которое мы запрещаем |
| `503` | `{"detail": {"error": "no_code_available", "message": "…"}}` | на этом номере одновременно открыто слишком много верификаций, чтобы выдать этой отдельный код |
| `401` | `{"detail": "Invalid or missing token"}` | |

`no_route_available` — это ответ, а не сбой. Читайте его как «не сейчас, не этим шлюзом»: маршруты, которые он бы предложил, — это те, чьё предусловие не смогло доказать себя за последние несколько секунд.

## POST /verifications/{id}/route

Выбрать маршрут. **Это единственный момент, когда верификация обзаводится маршрутом**, и обзаводится ровно одним: список для выбора — не лицензия на прыжки между маршрутами.

```http
POST /verifications/9/route
Authorization: Bearer <your token>
Content-Type: application/json

{ "route": "sms_in" }
```

Предложение здесь доказывается заново, а не берётся на веру из ответа на создание, — доказательство протухает, а промежуток между предложением и выбором как раз и есть то место, где оно протухает.

### Ответ 200

```json
{
  "id": 9,
  "route": "sms_in",
  "status": "pending",
  "reason": null,
  "code": "4821"
}
```

🔴 **`route` — это та ступень, что фактически провела верификацию, и это не всегда та, что вы запросили.** Там, где верификацию ведёт сам шлюз, — сегодня это `tg_gateway`, — он проходит по лестнице, настроенной для оператора этого абонента, прежде чем ответить вам, начиная со ступени, которую выбрали вы. Если эта ступень абонента отклоняет, а следующая проводит верификацию, в этом поле будет названа именно следующая, и описывать на экране нужно именно её: сказать человеку следить за Telegram, когда Telegram его отклонил, — значит заставить его ждать не там, где в этот момент звонит телефон у него в руке. Лестница устаканивается **внутри этого ответа** — вас никогда не переводят на другой маршрут после того, как мы уже ответили.

**`status` и `reason` — вторая половина того же предложения.** Если лестница прошла до конца и ничто не провело верификацию, этот ответ говорит `"status": "failed"` вместе с `reason`, называющим ступени и то, что каждая из них сделала, — вместо `pending`, через который пришлось бы прорываться опросом. `reason` равен `null`, когда сказать нечего.

**`code` не равен null только на `sms_in`, и больше нигде.** Это маршрут, где отправитель — сам человек: он читает код с вашего экрана и отправляет его нам с номера, который верифицируется, поэтому вы обязаны уметь его показать. На всех маршрутах, которые ведёт сам шлюз, `code` равен `null` — выданный там код позволил бы подтвердить верификацию, так и не достучавшись до человека, а это и есть весь смысл верификации.

Покажите этот код. Не логируйте его, не храните дольше самой верификации и никуда сами его не отправляйте.

### Отказы

| тело | когда |
|---|---|
| `{"detail": "Verification not found"}` (`404`) | нет такого id для вашего приложения |
| `{"detail": {"error": "verification_failed" \| "verification_expired" \| "verification_confirmed", "reason": …, "message": …}}` (`422`) | эта верификация уже завершена. **Отказ необратим** — откройте новую верификацию, чтобы попробовать снова |
| `{"detail": {"error": "already_selected", "route": "…", "message": …}}` (`422`) | её уже ведёт этот маршрут |
| `{"detail": {"error": "route_not_offered", "route": "…", "message": …}}` (`422`) | этот маршрут не предлагался или больше не может доказать себя |
| `{"detail": {"error": "expired", "route": "…"}}` (`422`) | время вышло между двумя вашими вызовами |
| `{"detail": {"error": "refused", "route": "…", "reason": …, "message": …}}` (`422`) | ступень, за которую платит шлюз, была отклонена **до того, как связались с каким-либо вендором**, — у приложения нет права на трату, достигнут собственный потолок расходов шлюза, либо на этом номере было слишком много платных попыток слишком недавно. Ничего не было размещено и ничего не было списано; это не отказ вендора. `reason` называет, что именно это было |

## POST /verifications/{id}/check

Только для маршрутов, где человек читает код и вводит его обратно в **ваше** приложение. На `call_in` и `sms_in` человек действует в сети связи, а не здесь, и вы никогда не вызываете эту дверь.

```http
POST /verifications/9/check
Authorization: Bearer <your token>
Content-Type: application/json

{ "code": "4821" }
```

### Ответ 200

```json
{
  "id": 9,
  "status": "confirmed",
  "outcome": "confirmed"
}
```

| `outcome` | значение |
|---|---|
| `confirmed` | доказано. `status` равен `confirmed` |
| `wrong_code` | потрачена одна попытка |
| `no_attempts_left` | попытка, достигшая потолка, завершила верификацию. `status` равен `failed` |
| `expired` | окно закрылось |
| `already_confirmed` | уже было доказано ранее. Идемпотентно и дёшево |

Голое «нет» здесь намеренно не ответ: вы — барьер, у которого стоит человек, а «время вышло» и «неверно» значат для него разное.

Потолок неверных кодов — это настройка оператора `verification_max_attempts`, которая по умолчанию равна **5**. `404`, если такой верификации для вашего приложения не существует.

## GET /verifications/{id}

Истина в любой момент времени и источник истины для всего, что описано ниже.

```json
{
  "id": 9,
  "phone": "<the number being verified, normalised>",
  "status": "confirmed",
  "route": "call_in",
  "method": "call_in",
  "reason": null,
  "routes": [],
  "attempts": 0,
  "created_at": "2026-09-21T09:14:05Z",
  "expires_at": "2026-09-21T09:19:05Z",
  "confirmed_at": "2026-09-21T09:14:41Z"
}
```

| поле | значение |
|---|---|
| `status` | `pending` \| `confirmed` \| `failed` \| `expired` |
| `route` | маршрут, который вы выбрали, или `null`, если вы ещё не выбирали |
| `method` | **то, что фактически доказало верификацию**, при подтверждении. Не всегда совпадает с маршрутом, который её вёл, — см. ниже |
| `reason` | свободный текст при отказе, иначе `null`. Написан для человека; не стройте на нём ветвление |
| `routes` | **что осталось попробовать, и только при `failed`.** Пусто, пока верификация ещё ведётся, и пусто при подтверждении |
| `attempts` | сколько неверных кодов потрачено |
| `created_at` | когда открыта, ISO-8601 UTC |
| `expires_at` | крайний срок. Маршрут может приблизить его; ничто не может его отодвинуть |
| `confirmed_at` | когда доказана, либо `null` |

Кода нет ни в одном поле этого ответа — никогда, и его нет и в `reason`: из текста, приходящего от вендора или из исключения, код вырезается в момент сохранения, а не в момент чтения.

### `method` — это не `route`

`route` — это то, как шлюз провёл верификацию. `method` — это то, что её доказало, и эти два словаря различаются потому, что доказательства неравноценны по силе.

| `method` | что произошло | сила |
|---|---|---|
| `call_in` | пришёл звонок с номера, который верифицируется | номер звонящего утверждается сетью, а сети можно солгать |
| `sms_in` | пришло сообщение с номера, который верифицируется, с кодом внутри | событие прихода **и** секрет, которым атакующему тоже пришлось бы владеть |
| `check` | человек ввёл код обратно в ваше приложение | код дошёл до человека тем маршрутом, который его вёл |

Приложение, чьи ставки не терпят самого слабого из этих доказательств, может увидеть, что именно оно получило, и отказаться его принять. Именно ради этого поле и существует; если ваши ставки обычные — игнорируйте его.

### `routes` при отказе — это путь дальше

Ступень, которая отказала, завершает верификацию, и шлюз **не** переходит к другой сам. Переход — это ваше действие, а действию нужно на что опираться — поэтому верификация со статусом `failed` несёт в себе оставшуюся лестницу, заново доказанную в момент, когда вы её читаете, с отказавшим маршрутом, вычеркнутым по имени. Откройте новую верификацию и выберите из этого списка.

## Пуш

Необязательно. Шлюз может вызвать ваш эндпоинт, когда верификация достигает финального состояния, — так вы узнаёте результат, не дожидаясь следующего опроса. Он ездит на той же конфигурации `delivery_dispatch`, что и статусный вебхук SMS, — один URL и один bearer-токен на приложение, — и с этой стороны описан в [`delivery-webhook.md`](delivery-webhook.md).

```http
POST <your webhook url> HTTP/1.1
Content-Type: application/json
Authorization: Bearer <your token>

{
  "object": "verification",
  "verification_id": 9,
  "status": "confirmed",
  "method": "call_in",
  "reason": null,
  "occurred_at": "2026-09-21T09:14:41Z"
}
```

| поле | всегда? | значение |
|---|---|---|
| `object` | да | всегда строка `verification` |
| `verification_id` | да | id, который вернул `POST /verifications` |
| `status` | да | `confirmed` \| `failed` \| `expired`. Никогда не `pending` |
| `method` | да | как описано выше; `null`, если верификация не подтверждена |
| `reason` | да | свободный текст при отказе, иначе `null` |
| `occurred_at` | да | ISO-8601 UTC |

🔴 **Субъект здесь — в `verification_id`, а поля `id` вообще нет.** Это не случайность именования. Статусный вебхук для исходящего SMS несёт *свой* субъект в `id`, оба тела приходят на один и тот же URL, и оба используют слова `failed` и `expired` — так что получатель, завязанный на `id` и `status` (а это весь старый контракт), примет верификацию за сообщение и пометит не то, что нужно. Отвечайте `200` на всё, что принимаете; тело мы не читаем.

## Ловушки

### Опрос — рекомендуемый путь, и для подтверждения он же самый быстрый

`GET /verifications/{id}` — это источник истины. Пуш — ускоритель поверх него, и он **не мгновенный**: финальные состояния выметаются к приложениям тиком **раз в минуту**, так что подтверждение, случившееся секунду назад, может дойти до вашего эндпоинта только через минуту. Опрос видит его сразу.

Если человек стоит перед барьером и ждёт, когда его пропустят, — опрашивайте. Пуш используйте для сверки, а не для того, чтобы открыть ворота.

**Поэтому опрос — то, что мы рекомендуем, а пуш — опция.** Оба поддерживаются, и ни один не устарел; это наше суждение о том, к чему тянуться в первую очередь, принятое 22.09.2026. Опрос не требует от вас ничего — ни публичного адреса, ни проверки подписи, ни обработки доставки, пришедшей дважды, — а экран у человека и так уже открыт, так что опрос раз в секунду в пятиминутном окне — это десятки запросов, а не нагрузка. Берите пуш, когда у вас уже есть эндпоинт и вы хотите узнать результат, не дожидаясь следующего тика.

Доставка пуша — с максимальными усилиями, на тех же условиях, что и у SMS: до 3 попыток (настраивается), 10 секунд таймаут на каждую, 1 секунда, потом 4 секунды между ними, затем сброс. Перезапуск посреди повторов теряет его. Ничего не сохраняется, очереди нет.

### Пять минут, и часы — наши

Время жизни верификации по умолчанию — **пять минут** (`verification_ttl_seconds`, 300 с). У маршрута может быть собственное, **более короткое** окно, и тогда срок приближается под него; никакая конфигурация не может отодвинуть его дальше того, что вам сообщили при создании. Читайте `expires_at` и верьте ему, а не вычисляйте свой собственный срок.

### Отказ необратим

Верификация, которая отказала, закончена. Она не переоткрывается, не перевзводится, а счётчик её попыток не пополняется. Следующая попытка — это **новая** верификация, что заодно даёт человеку свежий код и заново доказанную лестницу.

### `expired` значит, что время вышло, — и это не единственный способ прождать зря

`expired` значит, что время вышло. Его `reason` — это `window_expired`, и сказать здесь больше нечего сверх самих часов: слово называет то поле, откуда оно взялось, потому что истечение **доставки**, о котором сообщает оператор связи, — это другой факт про другую вещь, и один из двух связан с деньгами.

Что **не** сообщается как истечение — это маршрут, который умер под уже открытой верификацией: тик завершает такую верификацию как `failed` с причиной, называющей маршрут, потерявший своё предусловие. Сказать это человеку, который позвонил вовремя и с правильного номера, — значит, что «время вышло» было бы сообщением шлюза о том, чего на самом деле не произошло.

### Будьте идемпотентны и игнорируйте то, чего не узнаёте

Результат может дойти до вас дважды — один раз пушем и один раз вашим опросом, либо дважды пушем после перезапуска. Применение его дважды должно быть отсутствием действия. Мы можем добавлять поля в любое тело, описанное здесь; игнорируйте те, которых не знаете, вместо того чтобы отклонять запрос.

### Инструкция на английском

`instruction` написан по-английски, и шлюз его не переводит. Если ваше приложение говорит с человеком на другом языке, вам стоит составлять собственный текст под каждый `route`.

✅ **Номер, на который абонент должен позвонить или написать, передаётся вам как данные**, в поле `number` рядом с `instruction`, начиная с 22.09.2026. Читайте его оттуда и пишите собственное предложение.

🔴 **Не восстанавливайте цифры из `instruction` регулярным выражением.** Это сделало бы наш английский текст негласной частью контракта и сломалось бы в тот день, когда кто-нибудь улучшит формулировку, — молча, на вашей стороне, перед человеком у барьера.

## Что развёртывание может провести сегодня

Указано для продакшен-развёртывания по состоянию на **25.09.2026**. Словарь маршрутов фиксирован и плоский. Все имена, которые знает шлюз:

| маршрут | кто действует | ведётся сегодня? |
|---|---|---|
| `call_in` | абонент звонит на номер шлюза; звонок не принимается | **да** — номер шлюза настроен и передаётся вам в `number` |
| `sms_in` | абонент отправляет код на номер шлюза | **да**, предлагается только когда ничто более дешёвое не доказало себя (SMS оплачивает абонент) |
| `sms_out` | шлюз отправляет код абоненту | **только для приложения с настроенным шаблоном верификации**, который задаёт оператор, — сегодня ни один не настроен; запросите, если хотите этот маршрут |
| `flash_call` | звонит вендор; код — последние четыре цифры номера звонящего | **подключён и настроен**; первый платный звонок в продакшене пока не наблюдался |
| `tg_gateway` | код приходит в Telegram | **да** — провёл код в продакшене 22.09.2026 |
| `tg_user`, `max_user`, `app_bot` | мессенджер-аккаунты | названы, но ничем не ведутся |

Какие из них предложат конкретному номеру, решается для каждого запроса отдельно — по тому, что способно доказать себя для этого номера в этот момент; узнавайте это из `routes`, а не из этой таблицы.

**Сначала Telegram, потом звонок — внутри одного выбора.** Когда вы выбираете ступень, шлюз проходит по правилу маршрутизации для оператора этого абонента **начиная с этой ступени**. Для МегаФона в правиле записано: `tg_gateway`, затем `flash_call`: выберите `tg_gateway`, и если Telegram отклоняет номер, когда мы просим его отправить сообщение, шлюз переходит к `flash_call` в рамках того же вызова `POST /verifications/{id}/route`. `route` в ответе называет ступень, которая доставила код, а `instruction` — то, что показать человеку. Ступень, которую правило не называет для этого оператора, ведётся сама по себе, без продолжения.

Если Telegram **принял** сообщение, а оно затем не было доставлено, или человек говорит, что ничего не пришло, пока верификация ещё `pending`, — автоматической второй ступени не будет: откройте **новую** верификацию и выберите следующий предложенный вам маршрут (см. [Отказ необратим](#отказ-необратим)).

Вендору сообщён адрес для отчётов о доставке (начиная с 21.09.2026), так что сообщение Telegram, которое он принял и не смог доставить, завершает верификацию с причиной, вместо того чтобы просто дождаться истечения часов.

## Почему это важно для абонентов МегаФона — уже сегодня

С **22.09.2026** шлюз не отправляет произвольный текст на номера МегаФона: `POST /sms/send` на такой номер принимается, а затем завершается как `failed`, с `error`, говорящим *"the route the rule names for МегаФон is tg_gateway, which cannot carry arbitrary text"* (маршрут, который правило называет для МегаФона, — это `tg_gateway`, а он не может нести произвольный текст). Оператор отклоняет наш маршрут SMS, а до этой даты такие сообщения выглядели доставленными для вас и никогда не доходили до человека. Поэтому код входа, отправленный через `/sms/send`, не доходит **ни до одного** абонента МегаФона. Через двери этого документа он может дойти — сначала через Telegram, потом через звонок. В этом и вся причина перенести сюда доставку кода.

## Что нам нужно от вас

| | |
|---|---|
| `app_id` | id вашего приложения в шлюзе (тот, на который указывает ваш API-токен) |
| `webhook_url` | полный абсолютный URL вида `https://…`, **только если** вам нужен пуш |
| `bearer` | токен, который мы отправляем как `Authorization: Bearer <token>` в пуше |

Это настраивает оператор. На вашей стороне разворачивать нечего, кроме самого эндпоинта, а эндпоинт не обязателен — приложению, которое опрашивает, вообще не нужна от нас никакая конфигурация, кроме своего API-токена.
