## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Решение владельца 26.09.2026: частные настройки приложения живут у приложения, общие — в «Настройках». Сейчас три записи с ключом app_id лежат на общем экране настроек сырым JSON: verification_templates (текст SMS с кодом), delivery_dispatch (вебхук отчётов о доставке + bearer), messenger_brands → apps (разрешённые бренды и бренд по умолчанию). Карточка — отдельная страница /admin/apps/<id>, не раскрывающаяся строка. Хранение прежнее: карточка правит свою запись в тех же настройках, валидаторы (template.validate, validate_raw routes, validate_brands, check_every_account_is_rate_bound) не меняются, миграции нет. Приёмы с экрана настроек (SG-33.1, doc-7): отказ не теряет ввод, bearer маскируется сторожем и восстанавливается по ключу.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [ ] #1 Из списка «Приложения-клиенты» по id приложения открывается его страница /admin/apps/<id>
- [ ] #2 На странице приложения редактируется текст SMS с кодом: подсказка о ровно одном {code}, счётчик символов и частей SMS; пусто = записи нет
- [ ] #3 На странице приложения редактируется вебхук отчётов о доставке (URL и bearer); bearer не показывается, сохранение без правки его не стирает
- [ ] #4 На странице приложения выбираются разрешённые бренды мессенджеров из заведённых и бренд по умолчанию
- [ ] #5 Сохранение на странице приложения меняет только записи этого приложения; записи других приложений в тех же настройках остаются как были
- [ ] #6 Отказ валидатора показывается у поля на странице приложения, введённое не теряется
- [ ] #7 В списке приложений видно, у какого приложения нет шаблона SMS (код по SMS ему не уйдёт)
- [ ] #8 На экране настроек verification_templates, delivery_dispatch и привязка приложений к брендам не редактируются, вместо них ссылка «настраивается у приложения»
