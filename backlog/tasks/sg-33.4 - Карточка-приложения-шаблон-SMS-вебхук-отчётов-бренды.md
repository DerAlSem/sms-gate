## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Решение владельца 26.09.2026: частные настройки приложения живут у приложения, общие — в «Настройках». Сейчас три записи с ключом app_id лежат на общем экране настроек сырым JSON: verification_templates (текст SMS с кодом), delivery_dispatch (вебхук отчётов о доставке + bearer), messenger_brands → apps (разрешённые бренды и бренд по умолчанию). Карточка — отдельная страница /admin/apps/<id>, не раскрывающаяся строка. Хранение прежнее: карточка правит свою запись в тех же настройках, валидаторы (template.validate, validate_raw routes, validate_brands, check_every_account_is_rate_bound) не меняются, миграции нет. Приёмы с экрана настроек (SG-33.1, doc-7): отказ не теряет ввод, bearer маскируется сторожем и восстанавливается по ключу.
<!-- SECTION:DESCRIPTION:END -->

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
0. doc-8 admin-apps — сшивка /admin/apps по факту кода (готово до правки).
1. GET/POST /admin/apps/<id>: три блока-формы — текст SMS (verification_templates), вебхук отчётов (delivery_dispatch), бренды (messenger_brands.apps). Каждый блок пересобирает всю настройку: запись этого приложения заменяется/удаляется, чужие — как были, порядок сохранён; тот же validate_raw и store.set_many.
2. Текст SMS: подсказка про ровно один {code}, счётчик символов и частей (GSM-7 160/153, иначе UCS2 70/67, {code} считается длиной кода); пусто = записи нет.
3. Вебхук: URL + bearer паролем; пустой bearer = прежний; пустой URL = записи нет.
4. Бренды: галочки из заведённых brands + бренд по умолчанию; отказ set_many (лимиты) — у поля.
5. Отказ — у поля, ввод не теряется.
6. Список приложений: id → ссылка; метка «нет шаблона SMS».
7. Экран настроек: verification_templates и delivery_dispatch убрать из разделов → строка «настраивается у приложения»; messenger_brands показывается без apps, при сохранении apps подставляются из хранимого.
8. Проверка: pytest, рендер, jsdom для счётчика; /code-review; doc-8 и doc-7.
