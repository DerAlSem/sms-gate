# Хендофф в SG-42: корневая причина найдена и ИЗМЕРЕНА — это не вендор

Продолжение `backlog/tasks/sg-42 - flash_call-сверка-с-code-отчётом-uCaller…`.
Принёсено из сессии gmb_v2 (разбор инцидента входа юзера парковки, верификация
118). Владелец дал добро на тест-звонки (2 × 0.8 ₽ исполнены).

## Что опровергнуто

Премиса задачи — «поле code у uCaller системно НЕ есть набранные цифры» —
НЕВЕРНА. Поле верно отражает запрошенный код. Ложный «different digits»
рождается на нашей стороне: **сверка идёт с уже стёртым кодом верификации**.

## Механика (одним проходом)

1. `check_verification` (app/db/queries.py:1569) при подтверждении пишет
   `code = NULL` — инвариант «код стирается при терминале».
2. `unresolved_rungs` (queries.py:1469) джойнит `v.code` к рунгу.
3. `_settle` (app/verification/flash_carrier.py:303) читает `row["code"]`,
   сравнивает `_digits_changed(info.code, code or "")` → `'6517' != ''` →
   «вендор выделил другие цифры», рунг failed, алерт оператору.
4. Живые люди подтверждают за 9–23 с, вендор решает судьбу звонка до минуты →
   добор ВСЕГДА позже подтверждения → все живые входы получают ложный
   mismatch. Истёкшие без ввода успевают свериться честно (код ещё жив) —
   потому «чистые» и «грязные» так чётко разделились (6/6 против 8/8).

Карриер-путь (`carry`) не виноват: он держит код в локальной переменной с
момента чтения — эхо сверяется с живым значением даже при гонке.

## Контрольные прогоны 08.10 (тестовое приложение `test`, номер владельца)

| | v121 | v122 (репро инцидента) |
|---|---|---|
| намайнено | 9050 | 6517 |
| эхо вендора (getInfo, все 60 с) | '9050' | '6517' |
| экран владельца | 9050 | 6517 |
| подтверждение | нет | да, через ~1 с после select |
| вердикт добора | carried | **failed «other digits»** |

Один и тот же честный вендор, противоположные вердикты, единственная разница —
стёртый код. Прогон v122 — точная реплика инцидента 118 (confirmed 16:43:06 →
рунг failed 16:43:12 при эхе '5096'): значит **намайненный код 118 был 5096**,
человек прочёл его с телефона и ввёл с первой попытки. Утечки нет.

Про «другие цифры» из Notes (v35=9279, v118=5096): это не «другие» — это и есть
намайненные коды тех верификаций. Совпадение «всегда, кроме случаев, когда
сравнивать не с чем» — ровно картина честного эха.

## Что это меняет в плане SG-42

- **AC#4 и пункт 6 плана переформулировать**: в спеку нельзя вносить «поле code
  вендора не есть набранные цифры» — это неправда. Правда: «сверка с полем
  вендора валидна только пока код верификации жив; терминальная верификация
  кода не хранит».
- **Пункт 3 плана (_settle) — да, и это ядро фикса**: не классифицировать
  mismatch при `row["code"] IS NULL`; исход по `call_status` (PLACED → carried,
  стоимость писать как раньше), честный reason вроде «verification ended before
  the vendor reported; digits not comparable». Минимальная правка — одна ветка.
- **Пункт 2 плана (карриер → UNRESOLVED-семантика)** — из этой премисы больше
  не следует: карриер ложных срабатываний не даёт. Оставить как есть или менять
  по соображениям робастности — решение сессии, не необходимость.
- AC#1/AC#2/AC#3 остаются в силе (поведение фикса то же).

## Замечание владельца (08.10, дословно)

«Вообще, нелогично, что мы код стираем, но ладно» — менять инвариант хранения
он НЕ просил. Альтернатива «снапшотить код в рунг на placement» — обсуждение с
владельцем, не самоочевидное решение; минимальный фикс выше его не требует.

## Регрессионный тест

Последовательность v122: create → select flash_call → немедленный check своим
кодом → дождаться добора → рунг НЕ «failed different digits». Плюс юнит на
`_settle` с `row["code"] = None` (мимо боевой базы).

## Как проверять руками

`ssh sms-gate`; `sqlite3 -readonly /opt/sms-gate/data/sms.db`; таблицы
`verifications` / `verification_rungs` (UTC; журнал — МСК). getInfo — через
`app.verification.ucaller` с bearer из settings store, на коробке; токены и
ключи не печатать. Журнал: `journalctl -u sms-gate` (пользователь в adm).
Тест-верификации 121/122 в боевой базе — мусор, ретеншн уберёт сам.

Выкат — только ship-sms-gate (слово владельца, см. план задачи).
