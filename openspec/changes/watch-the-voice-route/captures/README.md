# Вендорский референс на `AT+QCFG="ims"` — задача 1.1, добыт 20.09.2026

Внешне-контрактный гейт требует референс **до** декодера и до любого утверждения о
том, что модуль сообщает. Референс добыт, и он опровергает три утверждения самой
заявки. Ниже — что именно сказано у вендора, что из этого следует и чего вендор
не говорит.

## Что сказано

```
AT+QCFG="ims"[,<IMS_conf>]

Запрос без параметра:  +QCFG: "ims",<IMS_conf>,<VoLTE_cap>  +  OK
Запись:                OK | ERROR | +CME ERROR: <err>
```

| поле | тип | значения по таблице вендора |
|---|---|---|
| `<IMS_conf>` | integer | `0` — включать ли IMS, **определяется умолчанием из MBN-файла**; `1` — включить принудительно; `2` — **выключить принудительно** |
| `<VoLTE_cap>` | integer | `0` — VoLTE disabled; `1` — VoLTE enabled |

**Characteristics:** *«The command takes effect after rebooting. The configuration
will be saved automatically.»*
**Maximum Response Time:** 300 мс.

Пример из документа A — ровно наша последовательность 18.09: `+QCFG: "ims",0,0` →
`AT+QCFG="ims",1` → `+QCFG: "ims",1,1`, с комментарием вендора
*«VoLTE enabled, VoLTE session available»*.

## Что референс ОПРОВЕРГАЕТ в этой заявке

### 1. У первого разряда три состояния, и `0` не значит «выключено»

`proposal.md`, `design.md` и `specs/voice-route/spec.md` трактуют первый разряд как
булево «IMS включён на модуле» и вешают на его ноль самый громкий алерт заявки
(«IMS disabled on the module»). По таблице вендора ноль — это **не** отказ, а
заводское «решает профиль оператора (MBN)». Явное локальное выключение — это `2`,
и его на этом модуле не видели ни разу.

Отсюда три следствия:

- `0,1` — **здоровый** модуль: профиль включил VoLTE, и тревожить некого. Алерт на
  «первый разряд не равен единице» поднял бы ложную;
- лечение «кто-то с шеллом пишет настройку и соглашается на ребут» верно для `2` и
  для `0`, чей MBN IMS не включает, — но это два разных диагноза, а не один;
- замер 18.09 `0,0` значит «профиль решает, и профиль не включил», а не «кто-то
  выключил». Прежняя формулировка приписывала действию человека то, что было
  умолчанием.

### 2. Второй разряд вендор называет не «сеть допустила»

Заявка говорит про второй разряд «the network has admitted it», а `design.md`
строит на этом целую главу: *«`1,0` is the carrier: nothing local will fix it and a
reboot will not help»* — то есть называет адресатом оператора.

Вендор так не говорит **нигде**, и вдобавок противоречит сам себе:

- таблица параметров §2.3.1: `<VoLTE_cap>` — *«Indicates the capability of VoLTE»*,
  0 — выключено, 1 — включено;
- проза §1.3.1: *«You can check the IMS registration status by `AT+QCFG="ims"`»*.

«Возможность VoLTE» и «статус регистрации в IMS» — разные величины, и ни одна из
них не равна «оператор отказал». Наблюдение 18.09 (три минуты нуля вне сети, потом
единица) с обеими формулировками совместимо и ни одну не выбирает. Под гейтом
утверждение «второй разряд — ответ сети» не лицензировано: его надо либо снять,
либо оставить как названную гипотезу с ценой ошибки.

### 3. Задача 1.2 закрыта референсом — и открылся путь отзыва, которого никто не назвал

«The configuration will be saved automatically» — настройка **переживает** power
cycle, и ребут боевого модуля ради этого ответа не нужен.

Но документ A даёт дорогу, по которой она пропадает без всякого ребута по нашей
воле, §1.2.1:

> *«If an NV item of the MBN files is changed through AT command, when the MBN is
> activated or deactivated, the previously configured NV item will recover to
> default.»*

А §1.2.3: MBN выбирается автоматически по IMSI вставленной симки, и §1.2.2:
*«not all operator MBN files enable IMS by default»*.

То есть **смена симки или переактивация MBN молча возвращает `ims` к умолчанию
профиля**. Это ровно тот сценарий, ради которого заявка и заводит слежку, и он же
делает нецель «шлюз не перевзводит настройку» решением, а не очевидностью: теперь
известно, что есть штатный путь, по которому её снимет не человек.

## Что референс подтверждает

- **`AT+CIREG` не встречается в документе B ни разу** (грепом по всему извлечённому
  тексту, 11 042 строки). Письмо Quectel от 18.09 и живой голый `ERROR` сходятся с
  манулом: команды в этой линейке нет;
- **коды для задачи 4.2.** `+CME ERROR`: `3` — Operation not allowed, `4` —
  Operation not supported. `+CMS ERROR`: `302` и `303` — те же две. Фатальные для
  симки: `13` — SIM failure (это и есть авария 06.09), `14` — SIM busy, `15` — SIM
  wrong, `10` — SIM not inserted;
- **бюджет для задачи 2.2.** 300 мс максимума — команда отвечает из своей памяти,
  ряд встаёт в локальный бюджет, а не в сетевой;
- **риск задачи 1.3 — задокументированный механизм, а не догадка.** §1.3.2.2 «SMS
  over IMS»: регистрация несёт `+g.3gpp.smsip`, и §1.3 прямо говорит *«IMS network
  also supports SMS»*. Включённый IMS действительно способен увести доставку SMS с
  CS-пути — проверять живой входящей обязательно.

## Чего референс НЕ отвечает

- **что именно возвращает эта сборка на отсутствующую команду.** Документ B говорит
  общее: *«+CME ERROR: <err> … The operation is similar to ERROR result code»*, но
  не обещает голого `ERROR` вместо кода. Ответ даёт живой сэмпл 18.09 —
  `AT+CIREG?` → **голый `ERROR`**. Один сэмпл на одну команду; утверждать по нему
  «любая отсутствующая команда отвечает голым `ERROR`» нельзя, и классификация
  задачи 4.2 обязана принимать оба вида отказа;
- **отличает ли модуль отказ сети от собственной неготовности.** Не отличает: поле
  одно и двузначное. Различение, на котором стоит «две беды — два адресата», прибор
  не даёт;
- **роуминг.** В документе A о поведении `<VoLTE_cap>` в роуминге нет ничего —
  открытый вопрос `design.md` остаётся открытым;
- **через сколько после регистрации в сети появляется единица.** Задача 1.4 живёт,
  референс на неё не отвечает.
