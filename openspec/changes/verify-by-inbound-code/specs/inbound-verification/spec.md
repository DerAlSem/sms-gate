## Purpose

Verifying that a person holds a particular phone number, and choosing how to do it when the
gateway cannot deliver a message to that number. It exists because delivery is not something
the gateway can promise: an operator withdrew it for one whole network on 06.09.2026 and has
withdrawn it entirely before. The owning application asks for a number to be verified and is
never asked to know which route carried it.

## ADDED Requirements

### Requirement: The gateway chooses the verification method and says so in its answer

A verification request SHALL name only the number to be verified. The gateway SHALL choose
the method, and SHALL return that choice in the same response — never accept a request it
already knows it cannot fulfil and fail it afterwards.

When the method is an outbound code, the response SHALL say so. When the gateway cannot
deliver to that number's operator, the response SHALL instead carry the fallback in full:
the code to display, the number the subscriber must text, and when the attempt stops being
valid. The application SHALL NOT have to infer the fallback, look up an operator, or hold a
table of which networks work.

#### Scenario: A deliverable number
- **WHEN** verification is requested for a number whose operator the gateway can reach
- **THEN** the response names the outbound method and the verification is pending

#### Scenario: An operator the gateway cannot reach
- **WHEN** verification is requested for a number on an operator configured as undeliverable
- **THEN** the response names the inbound method and carries the code, the gateway's number and the expiry, in that one answer

#### Scenario: The application is not told the route
- **WHEN** any verification is created
- **THEN** the response describes what the user must do, and does not expose which SIM, modem or provider is involved

### Requirement: The code is generated by the gateway and is matched together with the sender's number

The gateway SHALL generate the code. An application-supplied code SHALL NOT be accepted,
because the party that matches an inbound message must be the party that knows what to match.

A verification SHALL be confirmed only by an inbound message that **both** originates from
the number being verified **and** carries that verification's code. Neither half alone SHALL
confirm anything.

This pairing is what makes a four-digit code sufficient, and it is normative for that reason:
a reader who sees the length alone will judge it too short. An attacker must already hold the
subscriber's SIM to send from it, and must additionally produce a code displayed only on the
subscriber's screen.

#### Scenario: The right code from the right number
- **WHEN** an inbound message carrying the code arrives from the number being verified
- **THEN** the verification is confirmed

#### Scenario: The right code from another number
- **WHEN** an inbound message carrying a valid open code arrives from a different number
- **THEN** no verification is confirmed

#### Scenario: The wrong code from the right number
- **WHEN** an inbound message arrives from the number being verified carrying a code that is not this verification's
- **THEN** the verification stays pending

#### Scenario: An application tries to choose the code
- **WHEN** a verification request supplies its own code
- **THEN** the request is rejected rather than silently honoured

### Requirement: A code is single-use and time-bound

A verification SHALL expire, and its code SHALL stop confirming anything once it has expired
or once it has confirmed once. A code that has confirmed a verification SHALL NOT confirm a
second one, and an inbound message arriving after expiry SHALL NOT revive it.

Codes SHALL be reusable across time — four digits is a small space, and forbidding reuse
forever would exhaust it — but two verifications that are open **at the same time for the
same number** SHALL NOT carry the same code, because an inbound message could then not be
attributed to either with certainty.

#### Scenario: A replayed code
- **WHEN** the same inbound message is received twice
- **THEN** the verification is confirmed once and the second arrival changes nothing

#### Scenario: A code arriving after expiry
- **WHEN** the correct code arrives from the correct number after the verification expired
- **THEN** the verification stays expired and is not confirmed

#### Scenario: Two open verifications for one number
- **WHEN** a second verification is opened for a number that already has one open
- **THEN** the two do not share a code

### Requirement: The application learns the outcome without polling the modem

The owning application SHALL be able to learn that a verification was confirmed, by a push to
its configured route or by asking for the verification's current state. Inbound messages
SHALL NOT be reachable only through the admin UI, which is where they are reachable today.

A confirmation SHALL be observable within seconds of the inbound message being read from the
SIM, because the person waiting for it is standing at a barrier.

#### Scenario: Confirmation is pushed
- **WHEN** a verification is confirmed and the application has a configured route
- **THEN** the application is notified without having asked

#### Scenario: Confirmation is polled
- **WHEN** the application asks for a verification's state after confirmation
- **THEN** it is told the verification is confirmed, and when

### Requirement: An inbound message that matches no open verification is kept, not consumed

An inbound message that confirms nothing SHALL still be stored as it is today. Verification
SHALL NOT delete, hide or reclassify inbound traffic that was not meant for it: the gateway
receives ordinary messages from people, and a person replying to a parking code with a
question SHALL still be visible in the admin console.

#### Scenario: An unrelated inbound message
- **WHEN** an inbound message arrives that matches no open verification
- **THEN** it is stored and visible exactly as inbound messages are today
